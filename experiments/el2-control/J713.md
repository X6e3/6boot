# The first J713 runs

On 29 October 2026 the EL2 module ran on J713 (MacBook Air 13", M4), one
boot per entry. Each image was REL3 (kernel 7.1.13-x6e3-rel3) with stage 2
built from this tree with `CFG="FB_SILENT_MODE SIXBOOT_USER
SIXBOOT_EL2_NATIVE"`; only the `x6e3.el2=` boot argument changed.

Build c1285aca856e576e, module 9a2054b4... (12700 bytes). The build ID is a
hash of the 22 source files and the module, so `tools/build_native.py`
gives the same ID from this tree.

| Boot | Entry | Return | Result |
| --- | --- | --- | --- |
| 82ff35f3 | preflight | 0 | E2RS v1, flags 3 |
| 2033e81b | brk | 13 | E2EX v2, one frame, restore mask 0x3ff |
| ef683cdf | guest | 22 | four frames, verdict 0, three HVCs, restore mask 0x3ff |

Every time, Linux started at EL2 afterwards and KVM came up. The kernel log
shows the same error lines in all three boots.

## The guest run

Offsets are from the module's load address, which changes every boot.

| # | Exception | ESR | From | ELR | Symbol |
| --- | --- | --- | --- | --- | --- |
| 0 | BRK #0x6e32 | f2006e32 | EL2h, vector 4 | +0x310 | e2_expected_brk |
| 1 | HVC #0x6e33 | 5a006e33 | EL1h, vector 8 | +0x3080 | e2_guest_after_probe |
| 2 | HVC #0x6e37 | 5a006e37 | EL1h, vector 8 | +0x317c | e2_guest_after_signature |
| 3 | HVC #0x6e34 | 5a006e34 | EL1h, vector 8 | +0x3194 | e2_guest_after_done |

- A BRK's ELR is the BRK itself, so the handler resumes at +0x314. An HVC's
  ELR is already the next instruction, so the handler resumes there as it
  is.
- HCR_EL2 is 0x32488000038 in the BRK frame and 0x32480000000 in the three
  HVC frames: the guest ran with TGE, AMO, IMO and FMO clear.
- In frame 1, x0..x30 hold 0x200+n, as the guest set them. In frame 2, x0 is
  0x5a5, the reply EL2 wrote, and x1..x30 are unchanged. In frame 3, x0 is 0:
  the guest's own verdict that its registers came back.
- The 24 system registers the adapter saves before the call (VBAR_EL2,
  HCR_EL2, SCTLR_EL12, PAR_EL1, DAIF, TTBR0_EL2 and the rest) are equal after
  it.
- The whole guest entry took 7042 ticks of the 1 GHz counter, about 7 µs.
  Preflight took about 1.7 µs and the BRK entry about 3.3 µs.

## What it does not show

- Memory isolation. Stage-2 translation stays off (HCR_EL2.VM is 0) and the
  guest touches no memory.
- GXF. The adapter refuses to run when GXF is enabled. It was not, so
  HCR_EL2 writes under GXF are still untested.
- Repeatability. Each entry ran once, on the boot CPU, with interrupts
  masked.

The raw records (the /chosen properties, dmesg and their SHA256SUMS) are
kept outside this tree.

## 1 November: framebuffer smoke

Two boots of REL3 with the framebuffer smoke stage 2 (VISUAL.md in e0/):
6boot draws A/B/A from EL2 before Linux, with no Stage-2 and HCR.VM 0.

| Capture | Build | Result |
| --- | --- | --- |
| 20261101T022817Z, boot 9d072ecc | f9fe36a50e175b99 | REFUSED at TRANSLATE, reason ATTRIBUTE, 0 frames |
| d81adad294d88a5b-20261101T040021Z | d81adad294d88a5b | SMOKE_TRACE_VALID, 3 frames, error 0 |

Both times the context was restored (safety bits 15, HCR_EL2 0x32488000038
before and after, PAR and DAIF back) and Linux booted normally.

- The first build translated the framebuffer with AT S1E2W, got PAR attribute
  0x40 and refused it as an unknown memory type. Nothing was drawn.
- 0x40 is Normal non-cacheable with XS=0 under FEAT_XS, and J713 has it
  (ID_AA64ISAR1_EL1.XS=1). The second build checks XS, reads the level-3 leaf
  back from the page tables (16 KiB page, AttrIndx resolving to MAIR 0x44) and
  accepts it. 114 samples across the drawing band all came back the same.
- Framebuffer 0x103e1be8000, 2560×1664, stride 10240. Drawing the three
  frames took 2,251,284,447 ticks, about 2.25 s at 1 GHz.
- I watched A/B/A on the panel; the collector records that as my observation.
  The record itself shows that the drawing completed, not what the panel showed.

The build manifests say PENDING PHYSICAL TEST because they were written
before these boots.

The d81adad294d88a5b build ID is a hash over the whole source inventory at
build time (622 files), the configuration and the frozen REL3 inputs. That
inventory also held private working notes, and the documentation has changed
since the run, so recomputing the ID from this commit gives another value.
Every file the build compiles is the same as in the run. The ID itself is
checked against the build package's manifest (sha256 090e0a59...), not
against this commit.
